# ADR-0000: Phone calendar drag-to-reschedule and best-time heatmap

Status: Proposed (frozen work order; independent review pending)

The phone calendar supports day-only drops, matching the web calendar's day cells; neither provides time-slot drops. Dropping preserves local hours and minutes and rejects nonexistent local times by round trip. A confirmation sheet uses the existing WhenPicker and reschedulePost route. Move to… and the row accessibility action open the same sheet without requiring a drag.

React Native responder props provide drag capture after a 400 ms Pressable hold, without adding a gesture library. The hook tracks row versus wrapper ownership because a stationary hold releases through Pressable, while Fabric grants the wrapper before terminating Pressable. Cancellation clears the drag on scope changes, list disappearance, row unmount, navigation, termination or window changes. The week targets appear as an absolute overlay, keeping the held row in place, and measure after layout. Month targets use window-coordinate measurements. Native simulator validation of responder takeover remains necessary.

The frozen pair `{expectedAt, scheduledAt}` is the route's compare-and-swap idempotency key; it has no separate idempotency header. Replay is only conditionally a no-op: `packages/db/schema/supabase/0308_social_team_publishing.sql:104-114` checks lead time and publishing state before timestamp equality. A retry can therefore be refused even if an earlier request committed.

Server rows remain separate from per-post optimistic entries. Rendering overlays each entry's chosen time onto only that post. Undo deletes only that entry and exposes the latest server row; it never restores an array snapshot. Entries and replies are guarded by per-entry tokens and a user/brand/API epoch, not the list-load generation. Refreshes, filters and range navigation preserve pending moves. User/brand/API changes and unmount clear entries and timers; late results cannot update the new scope. Successful moves and resolved reads invalidate older list loads before reloading.

An ambiguous reply is followed by re-reads rather than undo. `apps/mobile/src/lib/fetchWithTimeout.ts:22-30` aborts only on the phone; `packages/db/schema/supabase/0352_get_social_post.sql:12-15` reads a snapshot without waiting for an outstanding scheduling transaction. An old time therefore keeps the move pending: the PATCH can still commit after that read. Automatic checks use bounded delays of 2, 4, 8 and 16 seconds. Afterwards the pending state remains, with manual Check and a frozen-pair Try again. A single request per entry prevents overlapping reads or retries. Every non-success replay is re-read, never treated as proof of refusal. Retry disappears inside the 60-second lead-time window. Closing the sheet does not discard a pending entry.

Resolution uses actual status before comparing timestamps. Canceled means cancelled, not started; draft/unknown means no longer scheduled; published/failed or a non-pending scheduled target means publishing has started. A scheduled post at the new instant confirms success; a third instant resolves to the server time. A 404 resolves to gone. Cancelled and unscheduled results make no claim about whether the original move committed. All non-success resolutions offer Reload. Timestamp comparisons use Date.parse so equivalent timezone representations match. Messages name the post and use the existing announcement hook without live regions.

The best-time heatmap follows the web's evidence threshold and score scale, with four accent tints, contrasting text, and explicit scores or dashes. Days run down a fixed label column; hours run across one horizontal scroller with 44-point cells. Account/API identity travels with loaded insights so stale account data cannot mount or announce under a new selection. Re-tapping the selected account preserves its data. The first data mount announces a summary; cell selection announces detail.

Work-order interpretation: E2's final sentence reverses its explicit orientation, so hour headers and day row labels follow E2's main requirement and the web. The under-500-line rule applies to new and edited feature files; the existing ten app locale catalogs already exceed that limit and retain their required structure. ADR number 0000 follows the explicit frozen work order.

A pending row retains a Check button after its sheet closes. This reopens the frozen attempt and performs a read, preserving access to manual recovery after automatic checks finish. The work order does not specify that re-entry control.
