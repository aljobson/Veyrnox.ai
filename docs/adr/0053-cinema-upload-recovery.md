# ADR-0053 — Recover missed Cinema upload completion

Status: Proposed, 25 September 2026. Extends ADR-0052.

A missed Stream callback currently leaves a private video waiting until its creator manually refreshes. Add a bounded pass to the existing five-minute Worker cron. Read only recorded Stream UIDs through the existing ten-second, 64 KiB adapter and persist the same validated observation used by manual refresh and signed webhooks. Never create another video, infer an unknown UID, return an upload capability, publish content or free storage capacity.

Migration 0138 adds private polling metadata to the forced-RLS upload table. Service-only `claim_cinema_upload_checks(UUID)` claims at most twenty uploading/processing rows using row locks and SKIP LOCKED. Claims remain unavailable for five minutes and are ordered oldest claim first, so failed entries cannot monopolise the next batch. Repeating a still-current claim returns the same minimal ID/UID list. Claims are transient scheduling tokens, not permanent business-operation receipts; replacing an expired claim may make an older key reusable. That only schedules another read. Four reads run concurrently; all work is awaited. The twenty-entry limit yields a full pass of the current 100-reservation cap in roughly twenty-five minutes when the five-minute cron runs normally. Scheduling is best effort, not an SLA.

A separate completion RPC records one outcome per claim. Replays cannot change it; late results cannot overwrite a newer claim's outcome. Provider or database failures are isolated per entry and retried on later runs. A crash before completion leaves the old checked timestamp intact. Existing observation ordering and terminal-state guards resolve races with callbacks and manual refresh. Ready/error rows stop polling. Pending-upload responses remain uploading; no fabricated completion or expiry-based deletion occurs.

The existing fifteen-minute recovery snapshot gains aggregate counts only: checks overdue forty minutes, failed checks, provisioning older than five minutes, processing older than three hours, and error/expired uploads requiring cleanup (fifteen-minute grace after upload expiry). Existing finance/recovery counters and heartbeat semantics are unchanged. The existing watcher accepts pre-migration snapshots during deployment, but requires the entire Cinema group once any field appears. Its existing incident workflow can surface these counts; no new messaging integration is configured. Logs contain event name and counters, never provider responses, UID, user identity, grant or token. Missing/disabled recovery is detectable from outstanding rows becoming overdue even if no cron heartbeat can be written.

## Rollout and remaining work

`CINEMA_UPLOAD_RECOVERY_ENABLED=false` is the independent deployment gate until the owner applies 0138. Configure the scoped Stream credentials and test in an isolated environment before enabling it. Once enabled, leave recovery on when pausing creator-facing flags, so in-flight uploads finish. No credentials, provider resources, live upload data or production gates are changed here. No new dependencies or browser/API endpoints.

This closes the missing scheduled status-recovery implementation, not G06 or G10 overall. Unknown provisioning results still require operator reconciliation. Provider-first deletion, cancellation/replacement, account erasure, retention policy, rights/safety review, live integration tests and signed playback remain outstanding. A failed/expired reservation still counts against capacity. Never remove its database row to silence an alert or reissue a billable upload without checking the provider.

## Validation and security record

Trust boundary: scheduled server work reads existing private media identifiers and the provider's authenticated status; no new client authority. Data: claim UUID, claim/check timestamps, success bit, public aggregate operational counts. Finance: no credit/ledger mutation; reads do not reserve new media. Tests cover bounded concurrent batches, failure isolation/redaction, malformed provider/DB responses, default-off behavior, claim concurrency/replay/expiry, fairness, stale completions, terminal observations, ACLs and unchanged private content/credits. Isolated Postgres replay and ledger acceptance run in CI. Mocked provider tests do not establish live Stream behavior. See the operations runbook for failure handling.
