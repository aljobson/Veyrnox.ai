# ADR-0301: Kling O1 reference video templates

Date: 2026-10-29.
Status: accepted for inactive implementation; activation pending host proof.

## Decision and evidence

Add catalog model `kling-o1-reference`, named **Kling O1 · Reference**, using
`fal-ai/kling-video/o1/video-to-video/reference`. Evidence read on 2026-10-29:
[API schema](https://fal.ai/models/fal-ai/kling-video/o1/video-to-video/reference/api)
and [model pricing](https://fal.ai/models/fal-ai/kling-video/o1/video-to-video/reference).
The documented price is $0.168 per output second: $0.84 for 5 seconds and $1.68
for 10 seconds. The catalog stores the 5-second unit cost and the standing
floor gives `ceil(0.84 / 0.01796) = 47` credits; the existing duration multiplier
charges 94 credits for 10 seconds. No app-layer pricing rule is added.

The payload contains `prompt` (up to 2000 characters), required `video_url`,
required `image_urls`, `duration` (`'5'` or `'10'`), `keep_audio: false`, and
`aspect_ratio: 'auto'`. There are no `elements` or editable audio settings.
The provider supports up to four pictures together with elements; our product
contract admits two pictures in an ordered image list. The existing ADR-0263
`MULTI_REFERENCE_ENABLED` path is authoritative: absent/off permits one picture,
on permits two, with no model exception or deployment flag change. Templates
require both pictures for their intended result, so that workflow requires the
existing flag to be enabled by the host before activation.

## Source admission and templates

Keep MP4 width and height from `mp4Info` in resolved video dimensions. Require
proven `videoSeconds >= 3`; a finite conservative `seconds` value cannot stand
in for unknown visual coverage (`source_length_unknown`). Short clips return
`source_too_short`. The existing conservative `seconds <= 10` upper bound stays
in place. Both sides must be between 720 and 2160 pixels inclusive; unreadable
dimensions return `source_size_unknown`, and out-of-range dimensions return
`source_resolution_out_of_range`. These checks run before debit and apply only
to records declaring the new bounds; existing image and LatentSync rules remain.
The `source_too_short` and `source_resolution_out_of_range` copy is tied to this
model’s 3-second and 720–2160-pixel bounds. Before another record reuses either
code, make its copy bound-agnostic or interpolate the applicable limits.

The public capability view, browser fallback and developer OpenAPI expose
`minSeconds`, `minSide` and `maxSide`. Web Create and mobile Create show the same
translated duration range and per-side size guidance. Mobile preserves these
limits on each slot, translates explicit reference/start/end labels through
shared web keys, and keeps picked video dimensions. Its pre-check rejects known
short clips or out-of-range dimensions before upload; non-positive durations
and unknown metadata pass
to the authoritative server checks. Both new server errors reuse web translations.
Mobile-only pre-check messages live in a new English area plus all ten app
catalogs; shared messages are generated by `sync-web-i18n.mjs`.

The provider documents MP4/MOV, 3–10.05 seconds, 24–60 fps and up to 200 MB.
For video slots declaring `minSeconds`, both pickers explicitly say MP4 only,
and the web file input accepts `video/mp4`. Mobile already permits only MP4
video uploads. QuickTime sources cannot prove visual duration through the current
server reader and fail these minimum-duration checks with `source_length_unknown`.
Existing slots keep their shared format guidance. The app retains its existing
100 MB video cap and chooses the stricter 10-second limit. FPS is not probed. An unsupported frame rate may pass local
checks, fail at fal, and use the existing provider-failure refund path. No ledger,
RPC, webhook, refund or route-allowlist behavior changes.

Six original `ref-*` templates retain the source video's motion while using
`@Image1` for material/style and `@Image2` for palette/lighting. Picture ordering
is therefore part of the prompt contract. They are separate from
`SOURCE_TEMPLATES` and preserve existing community prompt rules. Their needs and
the reference-picture label and new errors are translated into all eleven
locales. Without showcase clips, they stay out of `PRESETS`, the picker and
`/api/presets`; `templateById` still resolves direct Create links once active.
The phone uses that same preview-filtered feed and retains the template needs
hint on the image slot alongside the required video slot. The static i18n audit
has one exact-module rule for canonical prompts and the fixed model name;
display fields remain audited, with regression coverage.

## Inactive launch and activation checklist

Migration `0405_kling_o1_reference.sql` inserts/upserts the row with
`active = false`. The builder does not apply migrations, call fal or other paid
APIs, flip flags, or create preview clips. The static token row is marked
`staged: true`, so public fallback lists omit it while name resolution and
capability lookup remain available. Activation requires a later migration.

- The host runs a staging probe with a total spend cap of **$5**, including
  the controlled failure below. With the existing multi-reference flag on in
  staging, run both 5-second and 10-second generations using one qualifying
  video and two pictures. Check ordering and the output.
- Read the fal invoice to confirm billing per **output** second and the assumed
  $0.84 / $1.68 costs. Stop within the same cap if observations disagree.
- Submit a 2-second video with otherwise valid inputs: expect
  `source_too_short` before any debit, and verify no debit was recorded.
- Separately submit a controlled provider failure that passes local checks:
  a 20 fps, 5-second, 1280×720 clip (below fal's 24 fps minimum), with the two
  pictures. Prove debit → failed job → `refund:provider_failed` (or
  `refund:submit_failed`). Include any cost in the same $5 total cap.
- Run `npm run check:capabilities` and verify the live schema contract.
- Supply and review preview clips before listing the templates.
- Remove `staged` from the Kling O1 reference row in `app/veyrnox/_lib/tokens.js`
  when activating the model so public fallbacks can list it.
- Enable the catalog row in a later activation UPDATE migration, using the
  exact positive `ROW_COUNT` DO-block guard from
  `packages/db/schema/supabase/README.md`. Use a replay-safe identity predicate
  and assert exactly one affected row. Confirm the existing multi-reference
  flag supports the intended two-picture workflow before activation.

Builder verification: `npm test`, `npm run lint`, `npm run typecheck`,
`node scripts/check-catalog-update-guards.mjs`,
`./scripts/check-migration-numbers.sh`, and `npm run check:vey-knowledge`.
Mobile verification from `apps/mobile`: `npx tsc --noEmit`, `npx jest --ci`,
`node scripts/gen-en-registry.mjs --check`, and
`node scripts/sync-web-i18n.mjs --check`.
Run `npm run sync:vey-knowledge` after copy changes. The host additionally runs
`npm run build`. Ledger acceptance is not required because no RPC changes.
