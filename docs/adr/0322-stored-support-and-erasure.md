# ADR-0322 — Stored support inbox and account erasure

Status: accepted for implementation; owner review pending.

Support intake is a DB enable switch, off by default. The authenticated `/api/v1/support/tickets` endpoint takes subject, category and plain-text body, requiring an idempotency key. Middleware identity is the only accepted identity; email comes from the user record. All support writes use advisory key (431,0), separate from the (427,0) roles/switches/plans lock. A user-row lock serializes the five unresolved ticket cap and one-per-30-seconds limit. RPC also checks the switch. There is no account link, public form, HTML renderer, email send or AI agent. Owners/support may read and write; all admin routes retain the four gates, and every admin RPC rechecks is_admin and the appropriate support permission.

Tickets have open/pending/solved states and an owner/support assignee. Replies are stored, not delivered. Resend delivery is a follow-up requiring the owner's explicit yes. Agent runs are an empty append-only log plus a service-role-only ingest RPC; it records structured action/outcome/status and never invokes an agent or sends a reply. Agent summary is generated from ticket ID/status/action, with a CHECK and length cap. Inbox/thread use keyset pagination; the page labels the latest 100 agent runs explicitly.

User intake uses support_intake_receipts with primary key (user_id, idem_key), forced RLS and no direct grants. These receipts are deleted by the same eraser on soft erasure and BEFORE DELETE; the FK also cascades on hard deletion. Admin writes alone use immutable admin_mutation_receipts, keyed and queried by (actor_user_id, idem_key). Customers never acquire an admin receipt or audit FK. Administrator audit references deliberately retain RESTRICT, so referenced administrators must use soft account erasure, not hard DELETE (ADR-0318). A real intake followed by hard deletion of a normal provisioned customer is covered by the acceptance script.

Mutations use idempotency receipts; private subject/body are SHA-256 hashed in receipts, never copied to immutable audit. Support audit reasons are the fixed operation codes support-reply, support-status and support-assign, rather than free text, so support audit payloads contain only IDs/statuses. Existing administrator identity columns retain their usual accountability meaning. This is an explicit narrowing of the general free-text reason contract to prevent unerasable copies of customer content.

Erasure is real: both the NULL-to-non-NULL users.deleted_at transition and a BEFORE DELETE trigger on users invoke the non-public `private.erase_support_for_user(uuid)` definer. It sets a transaction-local erasure marker. Append-only triggers admit only exact body/author_label/author_user_id or summary tombstones, checking the target user and equality of every other column. The hard-delete trigger runs while ticket ownership is still present, tombstoning ticket email/subject and messages/agent summaries before FK SET NULL loses that link. Production account deletion still uses the ordinary soft-erasure RPC. One additional exception permits a pure author_user_id SET NULL only after its parent user is gone (the FK hard-delete action); it also tombstones the author label while retaining the reply. Arbitrary FK clearing while the user exists, other updates, message deletion and truncation still fail. Service role has no table writes or direct execution on the eraser, so setting the marker alone grants no authority.

Two privacy refinements to the frozen schema are explicit: messages have nullable author_user_id to identify an author's messages across tickets; and erasure tombstones all messages in the person's tickets, including administrative quotes. User-authored messages in other tickets are also erased. When the departing person is an admin, their replies in other users' threads retain their bodies but lose author_label and author_user_id; those threads' support history remains usable. Tickets lose email/subject and user_id; agent summaries become [erased]. Other authors' unrelated tickets remain intact. Assignee UUIDs retain their reference to the tombstoned user; the departing author's message UUID references are cleared. No subsequent reply/log write can repopulate an erased thread. Tickets/messages and intake receipts have user FKs and belong in the account-deletion classification; agent runs reference tickets, not users.

Proof: focused `adminSupport.test.mjs`; host runs `test-admin-panel-support.mjs`, including actual prepare_account_deletion/erase_account with customer text quoted in an admin reply, not merely a direct soft-delete update. It also checks gates, read/write permissions, limits, idempotency, immutable logs, bounded metadata, forbidden erasure access and replay.
