# ADR-0358 — Pro editor: FilmCraft embedded on its own origin

- **Status**: **Proposed 2026-11-19.** The tooling (P1a, commit `850a2f171`) is built and flag-off; nothing is routed, hosted or deployed. The owner accepts this by merging the change. The CSP additions below take effect only when the child origin is created.
- **Related**: ADR-0060 (per-request CSP, no `'unsafe-inline'`), ADR-0080 (the browser timeline editor), ADR-0255 (mobile hosted editor), ADR-0346 (zero-credit local jobs), CLAUDE.md ("Adding a host means an ADR", Worker size and binding budget).

## Context

FilmCraft (github.com/storytold/filmcraft, release v0.20.1) is an open-source (MIT OR Apache-2.0) non-linear video editor written in Rust. It ships a WebAssembly build that runs the whole editor in the browser: `filmcraft_web_bg.wasm` is 50,019,301 bytes, with a small JS glue file and an `index.html` that has two inline scripts. Project files are JSON (`.fcproj`, schema 17) that reference media by path. The project's name and logos (ArtCraft, FilmCraft) are not covered by the open licence (its NOTICE).

The owner asked to bring it into the Video Editor on web and mobile. A static audit of the release and a local spike (2026-11-19, notes outside the repo) found:

- The wasm exceeds the Workers Assets limit of 26,214,400 bytes per file, so it cannot live in `.open-next/assets` or the Worker script (the script is already near its size budget).
- The upstream parent bridge (`?host=parent`) works only when the parent has the same origin as the editor frame; it checks `event.origin` and `event.source` and posts only to that parent.
- Autosave and imported-media copies write to the origin's OPFS storage even in host mode, and no switch turns that off. A shared origin would let one account's project reach the next account on the same browser.
- `filmcraft:save` carries a name, bytes and `saveAs` only. Save, Save a Copy and the old-schema upgrade backup cannot be told apart from it.
- The editor reloads itself in two places (WebGPU failure, fatal overlay); there is no telemetry endpoint, and no network access beyond import-from-URL.
- On an iPhone simulator it runs but shows the desktop layout, so it is not a phone editor.

## Decision

1. **A separate origin, not the Worker.** The editor is served from `pro-editor.<apex>` out of external static storage (an R2 bucket on a custom domain, or equivalent), with a `_headers` rule set generated by `scripts/build-pro-editor.mjs`. The Worker is unchanged and its size is not affected. Creating the DNS record, certificate and bucket is an owner action.
2. **Three layers.** Our app (apex) frames our own `host.html` on the child origin; `host.html` frames FilmCraft same-origin with `?host=parent` (so the upstream bridge works unmodified). The app talks only to `host.html`, over a versioned `postMessage` protocol (`veyrnox.pro/1`) with exact keys, exact `event.origin` and `event.source` checks, size caps and a per-session id on every command. The apex never receives the FilmCraft object.
3. **Strict CSP, per document.** `host.html` and `purge.html`: `default-src 'none'`, `script-src 'self'`, `connect-src 'none'`, `frame-ancestors` the exact apex origins (production, staging, local), no `X-Frame-Options`. The FilmCraft document: `script-src 'self' 'wasm-unsafe-eval'`, `style-src` a hash of its one inline style, `connect-src 'self' blob: data:` (so import-from-URL and model downloads are blocked), `frame-ancestors 'self'` plus the apex origins, because CSP checks every ancestor. The two inline scripts are moved to external files by a reproducible post-process of the pinned zip (exact-match replacements; the build fails if upstream text differs). **No existing route's CSP changes.**
4. **A gate before the wasm.** The post-processed page starts the editor only if its parent is same-origin, exposes the host object, and accepts a single-use random nonce passed in the URL. Direct visits to the editor page or to `host.html` show a message and load no wasm.
5. **One editor at a time, nothing left behind.** `host.html` takes a Web Lock (`ifAvailable`, never queued or stolen) and holds it for the whole document life. It wipes the origin's OPFS and localStorage before the engine starts, on every restart, and on shutdown. A wasm-free `purge.html` does the same wipe after the app removes the editor frame (sign-out, token expiry, account change); it refuses while an editor holds the lock. Sign-out never waits for it.
6. **Restarts go through the host.** FilmCraft's two self-reloads are replaced by a validated host restart (3 per session, renderer chosen from a fixed list, a working renderer is kept).
7. **Every save is a candidate.** The host reports each `filmcraft:save` as an immutable candidate tagged with its engine number. Because upstream gives no operation identity, nothing is promoted to the project's current version automatically; the app will promote one only on an explicit user choice (app side, a later slice).
8. **Scope.** Desktop and tablet web only. Phones keep the native editor and receive Pro projects through import and export (a later slice). Stored projects use their own document-asset contract and revision-checked head, never the 32 KiB project document (a later slice with its own ADR and migration).
9. **Provenance.** Only the tagged release zip (sha256 `1cf3072e3f3b6535fcd024d6f6ab2a16cf7776345d868037dc630de0ad0dbbb8`; wasm `4359872b…10ff5`) is used and pinned in `pro-editor/pins.json`. The release signature is not yet verified. Upstream licence files and notices ship with the assets; no ArtCraft or FilmCraft marks appear in our UI ("Pro editor").

## Consequences

- No change to the Worker, its bindings, any existing route or CSP, or the credit and ledger rules. Nothing is priced; editing and export are local.
- A new origin to operate: DNS, certificate, bucket, cache headers, and one more place to patch when upstream publishes a release. An upgrade means re-running the build against a new pinned zip and re-reading the audit items above.
- The editor's local storage is wiped on every session, so recovery depends on the host's candidate saves, not on upstream's autosave.
- A 50 MB first load, WebGPU or WebGL2 required, single-threaded wasm: slower on phones and older GPUs.
- Open before the flag can be turned on: hosting and DNS, the app-side client and save storage, a tablet check on a real device, verifying the release signature, an attribution bundle, and a REA audit of the shipped wasm.

## Alternatives rejected

- **Same origin as the app**: shares OPFS and cookies with account data, and the 50 MB file cannot ride the Worker assets.
- **Port the features to our JS editor**: very large, duplicates upstream; revisit per feature only with a measured need.
- **Patch the wasm or rebuild from source** for explicit save operation ids and persistence switches: possible later, only with the owner's word and a new review.
- **FilmCraft's CLI for server rendering**: out of scope; Concat (ADR-0261) stays the server renderer.
