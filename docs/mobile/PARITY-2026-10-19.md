# Web-to-phone parity map

**Status:** Proposed 2026-10-19, against `main` at `a77f191f`. Built from five read-only audits of the web platform (Editor, creation tools, Publish, Cinema, and a route and platform census) compared with `apps/mobile/src`. Nothing was run on a device or against production, and the audits did not read every file; each area lists what they could not verify.
**Decision (owner, 2026-10-19):** every feature on the web must exist in the phone app. This reverses roadmap decision 2 ("no native multi-track timeline") and the "deliberately not built on the phone" rows in [spec/PRD.md](spec/PRD.md). Roadmap decision 4 (credits only through the stores, no web link-out) still holds and constrains several rows below.
**Reads with:** [spec/README.md](spec/README.md), [PLAN-2026-10-18.md](PLAN-2026-10-18.md), [USER-JOURNEY-2026-10-19.md](USER-JOURNEY-2026-10-19.md). This file supersedes `GAP-ANALYSIS-2026-10-17.md`, which is stale (it still lists Account as empty).

Sizes are S (days), M (a week or two), L (several weeks), XL (a quarter). They are the auditors' estimates for one engineer, not commitments.

## 1. The shape of the gap

- **Roughly 150 web editor files** run a CapCut-style editor in the browser. The phone has a three-feature server job (quick edit). This is the largest gap and has no proven route.
- **Cinema** has 23 feature rows; free viewing, comments, report and block are built. Most of the rest is built on the web but **switched off in production**, so phone screens for it would show nothing until flags change.
- **Publish** has 26 rows; about eight are built on the phone. Real use beyond the first network is blocked by provider approvals and owner steps, not code.
- **Create tools, Library and Chat** are partly built; the remaining work is options and parity, plus three hard problems (Enhance, Film master, draw-on-image).
- **Account and platform:** sign-in, deletion, appeals, report, credits, push and i18n are built. Passkeys, two-factor, password change, devices, brand kit, review links, developer keys and OAuth grants are not.
- **Navigation and first run** (slices N1 to N8) are still unbuilt and everything lands in them.

**Constraints.** Web editor limits: 16 tracks, 40 clips, ten minutes. Safari is "preview-only" in its own ADR; a WebKit export path exists with unit tests but there is **no real-device evidence** anywhere. The web credits dialog links to Stripe, which breaks the store-only rule. A web view has no sign-in bridge. Device files live in browser storage, not on the server.

**Options.** A: the web editor in a web view (fastest; export on iPhone unproven). B: a native timeline plus a new server renderer (largest; every effect rebuilt or turned into a paid job). C: a native shell for bin, Library, generation, stems, brand, review and credits, with the web engine in a web view for preview and export.

**Recommendation:** C, after Spike S1 below. Fallback if export fails on a device: B, or render on the existing Fly runner (unverified that it can run editor documents).

## 7. Hard problems and the spike for each

Each spike runs on a real iPhone and a mid-range Android phone, not a simulator, and ends in pass or fail.

| # | Problem | Pass | Fail means |
|---|---------|------|------------|
| S1 | Run the web editor in a web view with a bridged session; import clips, add a crossfade and text, export 1080p | Export under 3x real time; no web-view kill including after background; file has correct frame count and audio within 0.1 s; thumb trim works | Choose the native timeline plus server render (B), or the Fly runner |
| S2 | Passkeys on a native build | Enrol and sign in against staging | A server change for the app origin, or defer to the web |
| S3 | Native resumable upload of a 1 GB file to Cinema | Resumes after force-quit and after a network switch | Design a background-session module |
| S4 | Import shared web logic (character builder, film validators, templates) into the app | Bundles on both platforms; the existing Node tests pass on the same file | Copy and add a drift test |
| S5 | Chat image attachment: resize a 4000 px HEIC to 2048 px and send | Server accepts; price shows; one charge on replay | Orientation or EXIF lost |
| S6 | A long chat turn through iOS suspension | Reply recovered, one charge, no duplicate on retry | Design a recovery read |
| S7 | Draw-on-image mask to PNG at source size | Server accepts it as the same input | Another canvas library |
| S8 | Film Studio 16:9 master on device (1920x1080, 24 fps, exact size) | Dimensions and duration within a frame, under 60 s | A new server ffmpeg route |
| S9 | Enhance on device | After the web decision: a native face-landmark plus filter export matches the web quality review | Defer |

## 8. Dependencies that are not code

- **Flags off in production** that the phone needs: unlocks, Pass, credit subscriptions, voting, polls, retention, audience, rankings, creator analytics, device uploads, project media uploads, store billing, push, account deletion. Flags change only on the owner's explicit word, and production vars are at the binding cap.
- **Provider approvals:** Google data-access review, LinkedIn, X and TikTok acceptance, Instagram App Review. Owner step: register `https://veyrnox.ai/social/connect/mobile/<network>` at each.
- **Server changes the phone forces:** a plan source field on `GET /plan`; a Cinema Pass store path (migration, webhook, guard); a job-cancel route (a product decision, see `JOB-CANCEL-OPTIONS-2026-10-18.md`); possibly catalogue fields for seed, negative prompt and aspect ratio; possibly a server render path for editor documents.
- **Store rules:** App Store 3.1.1 for the Pass and unlocks; 1.2 for creator-uploaded video. Both need written plans before submission.

## 9. Owner decisions

**Decided 2026-10-19:**
1. **Editor approach: go with the recommendation.** Option C (a native shell with the web engine in a web view for preview and export), after Spike S1 on a real iPhone and a mid-range Android phone. If S1 fails, the fallback is a native timeline with server rendering (B); that choice comes back to the owner with the S1 result.
2. **First store release is full parity**, not a phased subset. Every row in this document is in scope for the first public release. TestFlight and Play internal builds still ship along the way as milestones; only the public release waits.
3. **Creator tools ship in the first store release:** apply, content drafts, submit, withdraw, device upload and analytics. This needs a written App Store 1.2 plan for creator-uploaded video and a Play AI-content plan before submission.

**Consequences the owner should know:**
- The public release date moves to after phases P1 to P8 and every flag below is on in production. The auditors' sizes add up to many months for one engineer; use two mobile sessions in separate folders to shorten it, never in the same folder.
- Production flags that must be on for parity to be real, each needing the owner's explicit word: unlocks, Pass, credit subscriptions, voting, story polls, saved and follows, audience, rankings, creator analytics, device uploads (Publish and Cinema), project media uploads, store billing, push, account deletion. Production vars are at the binding cap, so each needs a slot freed first.
- Each of those features should be proved on staging with the flag on before production.
- Provider approvals (Google, LinkedIn, X, TikTok, Instagram) and the Cinema quarantine scanner sit on the critical path and are owner work.
- Enhance is not live on the web; parity for it means the web ships it first, or the owner accepts an exception.

**Still open:**
4. Whether Cinema's built-but-off features get a staging-flag plan (needed now, to test them).
5. Analytics: none, or a consent screen plus an SDK.
6. Privacy export: stays an email request, or becomes self-serve.
7. Enhance: the web decision comes first.
8. Credit subscriptions in the stores: a new ADR, or left to the web.
9. Job cancel.

## 10. What the audits could not verify

Anything on a real device or in production; WebCodecs in the phone web views; real memory limits; whether the editor's logic modules run in the phone's JavaScript engine; the `/api/catalog` field set; whether phone parsers match real server responses (mobile ADRs 0121 to 0142 were proved against a mock); the Apple review stance on a wrapped web editor; the Cinema quarantine-scanner flag; the web credit-subscription screens; brand creation on web; and the ADR-0112 flag mapping.
