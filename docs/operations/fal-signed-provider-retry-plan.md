# One-image staging signed callback retry plan

Status: prepared and locally tested; not deployed, no provider submission made. PR #795 contains the completed controlled transport evidence and is green but remains unmerged. This plan addresses a different gap: real fal signature verification and provider-originated redelivery after a deliberate retryable response.

The design follows Donne Martin's [System Design Primer](https://github.com/donnemartin/system-design-primer#message-queues): assume repeated deliveries and persist the decision before acknowledging. One SQLite Durable Object coordinates the dedicated job's immutable provider mapping and a one-time fault marker. It is not a global admission lock or a new production callback implementation.

## Proposed owner-approved bound

One fresh dedicated staging job, one `fal-ai/flux-2-pro` image at 1024×768, `num_images=1`, the fixed teapot prompt in the consumer, and at most two staging credits. The current [fal model page](https://fal.ai/models/fal-ai/flux-2-pro) quotes $0.03 for the first output megapixel, so this 0.786432-megapixel image is expected to cost $0.03; verify current price, correct staging fal account, balance and active headroom again before launch. No credit purchase, sustained load, production migration or production activation is included. Earlier completed samples do not provide an unused budget for this new generation.

The relay and consumer expire within fifteen minutes. Capacity policy, ordinary application admission and queue publication remain disabled. Operator fixture DML creates exactly one debit/outbox/reservation, then makes the dedicated model inactive before commit. Fresh fixture ownership and model prefix are checked before queue recovery or claim. A Postgres STARTED fence permits at most one application submission attempt even if the wakeup is delivered again. This does not claim exactly-once provider execution.

## Prepared code

- `workers/staging-fal-signed-retry-worker.js`: verifies the exact raw body with the existing real fal Ed25519/JWKS verifier and configured staging tenant. Only one allowlisted job, staging origin, POST path and unexpired plan are accepted. Body length is bounded at 128 KiB with a five-second read deadline. Header/body provider ID mismatch is refused before coordination.
- `FalSignedRetryGate`: private RPC registration pins the provider handle once. An early verified callback with no mapping returns 409 without consuming the fault. After registration, exactly one matching verified callback returns 503 without invoking the application. Later callbacks forward the original signed bytes and headers to the staging application service binding. The application verifies the signature again and retains existing inbox/storage/ledger behavior. Redirects and forwarding outages return 503.
- `workers/staging-fal-signed-retry-consumer.js`: has no public dispatch route; rejects unapproved, non-staging, unlisted or ownership-mismatched wakeups before mutation. It checks the exact endpoint and bounded payload before the single submission, substitutes only the fixed relay callback URL, and registers the accepted handle through private DO RPC. A relay mapping error never discards accepted database evidence. A later duplicate can repair that mapping from the already-recorded database handle without resubmitting.
- `wrangler.fal-signed-retry-staging.jsonc`: separate staging relay, default disabled with no job/tenant/expiry. No fal, database or R2 secret on the relay; service binding targets only the staging application. Public callback signature verification is never overridden. The ordinary application imports no exercise code.
- `scripts/provision-fal-signed-retry-staging.sql`: operator fixture DML, not a schema migration. It requires idle disabled capacity and no pending dispatches/reservations. It does not submit to fal.

## Launch and observation

1. Require explicit owner approval of this one-image bound. Read the correct logged-in Chrome fal account, verify it is the account backing staging credentials, and confirm current cost, balance and available capacity. Do not retrieve or print keys. Capture application/consumer complete bindings, active versions, cron schedules and queue tuning. Confirm queues empty and database recovery/reconciliation clean.
2. Temporarily disable application schema recovery, preserving all other bindings. Run the guarded fixture SQL and read the new user/model/job IDs. Keep the model inactive. Bind that exact job to both expiring plans. Use the application's existing configured staging tenant ID rather than accepting a tenant from an incoming callback.
3. Deploy the separate relay with its explicit plan enabled and no submit credential. Dry-run first; verify its service binding is staging only. Confirm its namespace from deployment metadata. Generate a temporary consumer config from the captured full variables: exercise entry point, exact user/model/job/expiry, explicit provider-test approval true, existing queue settings and a cross-script CALLBACK_GATE binding with class_name FalSignedRetryGate and script_name veyrnox-fal-signed-retry-staging. Preserve its existing secret names without retrieving secret values. Add no cron or HTTP dispatch route.
4. Connect counts-only tails before publishing exactly one version-1 job reference to the real staging queue. Never publish another job to consume a replacement budget. Confirm one claim, one actual provider POST, accepted provider handle retained in database, private mapping registration and normal projection to SUBMITTED.
5. Observe a genuinely fal-signed callback returning deliberate 503 and a later separately received provider delivery reaching the real application. Record IDs, timestamps, signature-valid decision, returned status and fal dashboard delivery evidence; do not persist payloads, signatures, prompts or asset URLs. Do not label operator-forwarded replay as provider-originated redelivery. An early unmapped 409 is recorded separately from the intentional mapped 503.
6. Require one processed inbox event, STORED job, one private application-bucket asset, one original two-credit debit, no refund and released capacity. Inspect deterministic object metadata and actual authenticated Library availability if the dedicated test identity has a supported session. If it lacks that session, report Library validation as unmeasured rather than borrowing another user's session. A repeated signed delivery may prove terminal deduplication only while its timestamp is valid; never fabricate a fal signature.

fal's current [webhook documentation](https://fal.ai/docs/documentation/model-apis/inference/webhooks) specifies 2xx acknowledgement, retries for timeout/network/4xx/5xx, and no redirect following. Initial delivery timeout is fifteen seconds and retried deliveries allow 120 seconds. The relay bounds forwarding at 110 seconds. Exact backoff timing is measured, not assumed. Provider retention can outlast this fifteen-minute exercise; reaching expiry without successful delivery is a failed test requiring operator reconciliation.

## Stop and restoration

On UNKNOWN, rejected submission, mapping conflict, storage failure, drift or missing observed retry, stop publishing new references and preserve the original job/attempt/provider evidence. Never reset STARTED/UNKNOWN, auto-resubmit, or close a real-provider reservation as NOT_SUBMITTED. Normal provider/operator reconciliation governs an actual ambiguous submission. A STORED fixture is not refunded.

Restore the ordinary disabled consumer from captured full variables and its standard entry point; remove the temporary cross-script binding and exercise variables. Keep the relay available until the fixture is terminal or provider delivery expiry and recovery are understood; do not erase pending real work just to obtain green counts. Restore application recovery after fixture reconciliation. Disable the relay, retain its small ID/fault audit record, then remove its callback exposure when no provider delivery is needed. Retain financial rows and stored asset evidence. Compare complete bindings and cron schedules to baseline and run the ordinary staging health workflow. Record any intentional alert and subsequent resolution.

## Validation and scope

Eight tests passed in Cloudflare's Vitest Workers runtime: real Ed25519 verifier with generated fixture keys, tenant/body tampering rejection, early mapping, immutable handle conflicts, concurrent fault allocation, persistence across actual DO eviction, exact raw forwarding, relay outages, approval/ownership guards, and accepted-evidence preservation with duplicate mapping repair. Run `npm ci --prefix tests/fal-signed-retry-runtime --ignore-scripts` then `npm test --prefix tests/fal-signed-retry-runtime`; CI runs the same isolated pinned dependencies. Wrangler relay and consumer packaging passed locally; fixture provisioning passed a disposable Postgres rollback check. These tests use inert credentials, mocked JWKS/application/provider replies and no live provider traffic. Reticle is skipped for this operator/backend harness with no product UI change.

Passing this sample would establish one observed real provider retry path. It would not establish sustained throughput, production-account headroom, billing distributions, a 24-hour clean window or production activation approval. Production and staging fal accounts are separate per the owner, so staging billing evidence cannot be substituted for production evidence.
