# fal transport boundary validation

After PR #789, the next fault boundary is a provider POST whose outcome cannot be confirmed. `scripts/test-fal-transport-boundary.mjs` joins the real queue consumer, JavaScript fal adapter and PostgreSQL claim/evidence/recovery RPCs against a loopback HTTP fault server. The database must be a disposable localhost `rebuild_check`; all fixtures and policy changes roll back. The fetch boundary blocks every unexpected origin and redirects only the adapter's `queue.fal.run` request to that loopback server. Credentials are inert placeholders. No provider calls or live changes occur.

The server reads the complete POST before each fault. Paid and free cases cover a discarded reply, a truncated HTTP 200 JSON body, a stalled reply ended by the adapter's AbortController, and a discarded reply followed by a database evidence write whose acknowledgement is lost. Eight cases passed. Each observes exactly one received POST, UNKNOWN evidence with no handle, a DEBITED job carrying `provider_outcome_unknown`, no immediate refund or allowance return, and an unreleased capacity reservation. The attempted queue reference is acknowledged; a following reference is deferred. A later duplicate is acknowledged without another POST. Evidence acknowledgement loss repeats the database evidence write, preserving the provider POST count. Logs are checked for fixture prompts and placeholder credentials.

The test shortens only the local submission deadline to one second; the production consumer retains fifteen seconds. Socket faults are real local HTTP failures, but the server's receipt of a POST does not prove fal accepted or billed a request. Database transaction rollback is test isolation, not a simulation of a database connection outage. CI runs this suite after the pinned-payload suite and treats fal adapter changes as database-acceptance relevant.

Before closing the deployed transport gate, exercise this uncertainty boundary on staging with fresh dedicated jobs, an expiring exact allowlist, captured consumer configuration and controlled transport. Require one attempted submission, durable UNKNOWN evidence, no automatic resubmission/refund, preserved held capacity and clean reconciliation. Restore the ordinary disabled consumer and retain audit evidence; never reset STARTED/UNKNOWN rows. Any real fal acceptance or signed callback/redelivery exercise needs a bounded provider budget and separate account/headroom evidence. Sustained capacity and the continuous clean monitoring window remain open requirements.

Reticle is skipped because this test/CI change has no browser UI surface.
