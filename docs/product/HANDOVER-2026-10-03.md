# Veyrnox.ai: project recap and handover

Written 2026-10-03 for the next agent (Codex), after a long Claude session. It
describes what is true on `main` at `2861db4` and in production at that
moment. Anything that moves (open PRs, the pending migration run, flags) must
be re-checked before acting. The rules of the repo are in `CLAUDE.md`; read it
first, every rule there was learned the hard way.

## 1. What the product is

Veyrnox.ai sells AI video, image and audio generation, metered in Credits.
Every generation shows its price before it runs; a failed job refunds itself.
It runs as a Next.js 16 app on Cloudflare Workers (OpenNext), with Supabase
Postgres (EU) for identity, the ledger and all state, Cloudflare R2 (EU) for
media, Stripe for money, and fal, kie, OpenRouter, GrsAI and BytePlus as
generation providers. Everything money-related goes through Postgres
functions; the browser never touches Postgres directly.

The sibling product Veyrnox (a wallet) is a different company in a different
repo. `scripts/check-hard-wall.sh` fails CI if wallet vocabulary lands in the
marketing tree. Never mix them.

Where to read more, in this order: `CLAUDE.md`, `CONTEXT.md` (glossary),
`ARCHITECTURE.md`, `docs/product/IMPLEMENTATION-PLAN.md` (the backlog, by
track), `docs/product/ISSUES.md` (the audit list), `docs/adr/README.md`
(every decision, indexed), `ROADMAP.md`.

## 2. How work ships

- `main` deploys to production on every push (`deploy-production.yml`), one
  run at a time, with a health check and automatic rollback of the Worker.
- Production migrations are applied only by `apply-migrations.yml` on `main`,
  after the owner approves the run (ADR-0023). A migration name, once
  applied, is permanent. **Each run applies the files of its own commit**, so
  a stale waiting run must be cancelled when a later commit corrects an
  unapplied migration (this happened today; see §5).
- CI: `ci.yml` (build, unit tests, lint, guards), `ledger-tests.yml` (a full
  migration replay on Postgres 16 plus `scripts/test-*.mjs` plus 275
  acceptance tests), `hard-wall.yml`, `verify.yml`, `migration-ledger.yml`.
- Hourly and nightly watchers: `reconcile-watch.yml` reads the counts-only
  reconcile snapshot; `signup-gate.yml` checks the sign-up gate; a nightly
  pg_cron job raises on any ledger drift. `site-health.yml` every 15 minutes.
- Several agents work in this repo at once and `main` moves mid-task. Before
  starting anything: `gh pr list`, `git branch -r --sort=-committerdate`,
  `git worktree list`. Re-check as a separate step right before opening a PR,
  and after any long step. Today the same database step was built twice.
- Owner's merge style: every PR is reported with what was verified and what
  was not; the owner says "merge N". Migrations touching money get two
  independent reviews before the PR (a static SQL read and an adversarial
  fuzzer against a local Postgres). Keep doing that.

## 6. Core subscriptions (ADR-0064): where it stands and what is next

Decided by the owner (all in ADR-0064): tiers Starter $19/270, Plus $59/1,200,
Ultra $129/3,000, monthly; spend order Subscription then Free then Pack,
soonest-expiring first; no rollover; a cancelled subscription keeps its credits
to the end of the paid period; a failed renewal gets no grace period; an
upgrade takes effect now with a new billing period (old remainder expires, as
at any renewal); downgrades, annual-to-monthly and resubscription to another
plan wait for the period end; monthly-to-annual on the same tier is undecided.

Built and applied: the ledger bucket (C2, C3). Built, awaiting apply: the
subscription state and its ledger joins (C4 database slice, #507 + #509).

**Next slice: the Stripe adapter, routes and webhook, behind a flag that ships
off** (#507's text names it `SUBSCRIPTIONS_ENABLED`; check `wrangler.jsonc`
before adding one). Model it on Cinema Pass: `packages/adapters/stripe.js`
(already 513 lines; put new code in a new file), `lib/cinema/passApi.js`,
`app/api/v1/cinema/pass/*`, and the Pass branches of
`app/api/webhook/stripe/route.js`. The webhook must tell a credit
subscription from a Cinema Pass: the signed metadata kind, or which table the
subscription id binds to.

What the merged database functions require of the webhook (from two review
rounds; details in the comments on #508 and in #509's description):
- **Never pass one Stripe event's id to both `apply_credit_subscription_event`
  and `grant_credit_subscription_invoice`.** The log has one row per event
  id; the grant answers `EVENT_ID_ALREADY_USED` rather than silently granting
  nothing.
- Retry `invoice.paid` with a 503 while `SUBSCRIPTION_NOT_FOUND` or
  `SUBSCRIPTION_NOT_READY` and the event is young; the binding event may not
  have committed yet (the Pass code does this with `isYoung`).
- Alert an Operator on every refused paid invoice (`refused: true`): the
  customer paid and has no credits until someone acts.
- Cancel at Stripe after a dispute (`reverse_credit_subscription_invoice`
  ends the row) and after a cooling-off cancellation.
- Configure Stripe so plan changes match the decisions: reset the billing
  cycle on an upgrade; schedule every other change for the period end; refuse
  a second checkout while a subscription is live or running out.
- The merged grant always grants the row's own `credits` and does not check
  the amount paid against the plan or the plan on the invoice. Upgrades and
  downgrades are therefore not yet supported by the database. The closed
  #508 holds a reviewed design for that (plan on the invoice is granted and
  the row follows it; first invoice must match the checkout's plan; amount at
  least the plan price, or the step up for a paid-up upgrade; period bounded
  to one interval). Use it when plan changes are built; it needs a new
  migration once 0186/0187 are applied.
- Open before launch, not before building: Stripe's written acceptance of
  credit subscriptions (ADR-0064 open question 3); tax and consent wording
  from Finance/Legal; whether partial goodwill refunds should end a
  subscription (today a `partially_refunded` reversal is recorded only).

Then C5: plans on `/pricing` and `/app/credits`.

## 9. Working locally: what is not obvious

- There is no Docker or Homebrew Postgres on the owner's Mac. The acceptance
  suite and `scripts/test-*.mjs` run against an embedded Postgres 18
  installed into a scratch directory (`npm install pg@8.13.0 tsx@4.19.2
  embedded-postgres`, a `package.json` with `"type":"module"` in that
  directory, `initdb -U veyrnox -A trust`, `pg_ctl ... -o "-p <port> -k
  <short socket dir> -c timezone=UTC"`). CI is Postgres 16; PG 18 reports
  `ON DELETE RESTRICT` as 23001, not 23503. The server timezone must be UTC
  or one free-credit test is off by an hour.
- Full replay: `DATABASE_URL=... node scripts/replay-migrations.mjs` on a
  fresh database, then the `scripts/test-*.mjs` chain in the order
  `ledger-tests.yml` lists, then `node scripts/migrate.mjs` on another fresh
  database and `npx tsx --test --test-concurrency=1
  packages/db/*.acceptance.test.ts`. Drop and recreate the databases between
  runs; the chain is not re-runnable.
- The worktree has no `pg`; a symlink `node_modules/pg -> <scratch>/node_modules/pg`
  works for the scripts. Remove it afterwards.
- Signed-in pages locally: `next dev` has no Supabase. A stub on
  `127.0.0.1:54321` (the only origin dev CSP allows) serving its own ES256
  JWKS at `/auth/v1/.well-known/jwks.json`, `/auth/v1/settings`, `/auth/v1/user`
  and whatever `/rest/v1/rpc/*` the page calls, plus a signed session in
  `localStorage.veyrnox_supabase_session`, drives any `/app/*` page.
- Headless Chrome through `playwright-core` with `channel: 'chrome'` is how
  every UI change today was verified (computed styles, flows, screenshots).
  Chrome's virtual authenticator (CDP `WebAuthn.addVirtualAuthenticator`)
  drives passkey flows.
- Production reads: the Supabase MCP `execute_sql` on project
  `xdxdzmsztyzbnzeforxx` is fine for read-only checks. Never DDL, never
  writes. Staging is `yrqzwqywxfesmbvhzjgj` (us-east-2, test data only).
- A Cloudflare secret change makes the newest uploaded Worker version live,
  which can be a branch preview. After any `wrangler secret put`, confirm the
  live version is main's.

## 10. Verification standard the owner expects

Every report says what was checked and how, and what was not. "Tests pass" is
not enough on its own for anything user-visible; drive it in a browser. For
money code: a full local replay, the CI chain, the acceptance suite, and two
independent reviews before the PR, with the findings and their fixes in the
PR description. Never claim a watch, a deploy or an apply happened without
reading its result.
